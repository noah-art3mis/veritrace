# Standard fact-check representations and how VERITRACE maps onto them

Research for issue #121. Surveys the load-bearing representations the field uses – FActScore/SAFE, ClaimReview (schema.org), the Google Fact Check Tools API, AVeriTeC, FEVER/FEVEROUS, ClaimBuster, ClaimsKG, MediaReview, IFCN – and maps VERITRACE's bespoke graph schema (`lib/graph-types.ts`) onto each: where we align, where we silently diverge, and what emitting or consuming them natively would buy. Code citations are `file:line` against the repo at the time of writing; external claims cite the primary source.

## 1. The representations

### 1.1 FActScore

**What it encodes:** a long-form generation decomposed into *atomic facts*, each judged against a reliable knowledge source (Wikipedia in the paper). **Label vocabulary:** binary per fact – supported / not-supported. **Aggregate:** FActScore = the percentage of atomic facts supported by the knowledge source (0–100%); the automated estimator (retrieval + a strong LM) tracks human annotation within <2% error. Source: Min et al., *FActScore: Fine-grained Atomic Evaluation of Factual Precision in Long Form Text Generation*, EMNLP 2023, [arXiv:2305.14251](https://arxiv.org/abs/2305.14251).

FActScore's `postprocess_atomic_facts()` also *auto-corrects* decontextualization: it detects entities in the atomic fact absent from the source (spaCy NER) and string-replaces them back to the source's surface form. VERITRACE deliberately does the detection half only, emitting an advisory `injected` list instead of mutating the claim – documented with rationale at `lib/pipeline/audit.ts:14-33` (human-in-the-loop; injection is not always an error; string-replace is unsound across translation). This is the #15 divergence the issue references.

### 1.2 SAFE / F1@K

**What it encodes:** the successor pattern to FActScore for open-web checking – an LLM agent splits a response into individual facts, revises each to be self-contained, then rates it via multi-step Google Search reasoning. **Label vocabulary:** 3-way per fact – supported / irrelevant / not-supported. **Aggregate:** F1@K, which balances precision (fraction of supported facts) against recall relative to a hyperparameter K (the user's preferred number of facts). Source: Wei et al., *Long-form factuality in large language models*, [arXiv:2403.18802](https://arxiv.org/abs/2403.18802). VERITRACE's decompose-then-check pipeline and the `ClaimTally` "X of N supported" signal are explicitly SAFE-derived (`lib/pipeline/verdict.ts:119-124` cites "SAFE F1@K"; `lib/graph-types.ts:103`), and SAFE's *relevance* axis is mirrored in `ClaimItem.relevant` (`lib/graph-types.ts:82-89`).

### 1.3 ClaimReview (schema.org)

**What it encodes:** the de-facto publication/interchange markup for a finished fact-check. Type chain `Thing → CreativeWork → Review → ClaimReview`; core properties: `claimReviewed` (text of the claim), `itemReviewed` (a `Claim`, with its own `author` = the claimant and `appearance`/`firstAppearance` = where the claim ran), `reviewRating` (a `Rating`), plus inherited `author` (the fact-checking org), `datePublished`, `url`. **Label vocabulary:** none imposed – `Rating.alternateName` carries the publisher's own label ("True", "Pants on Fire", "Distorcido"), while `ratingValue`/`bestRating`/`worstRating` optionally place it on a numeric scale. Sources: [schema.org/ClaimReview](https://schema.org/ClaimReview), Google's markup guide [developers.google.com/search/docs/appearance/structured-data/factcheck](https://developers.google.com/search/docs/appearance/structured-data/factcheck) (which marks `alternateName` required and `ratingValue`/`bestRating`/`worstRating` recommended).

The crucial structural point for us: ClaimReview ratings are **dual-encoded** – free text (`alternateName`) *and* a bounded numeric scale (`ratingValue` on `worstRating..bestRating`). VERITRACE currently reads only the free-text half (see §1.4).

### 1.4 Google Fact Check Tools API

**What it offers:** two surfaces – (a) the **Claim Search API** (`claims:search`, the endpoint VERITRACE calls at `lib/factcheck.ts:17`), querying the ClaimReview corpus behind Fact Check Explorer, and (b) the **ClaimReview Read/Write API** (`pages`) for publishers to manage their own markup. Docs: [developers.google.com/fact-check/tools/api](https://developers.google.com/fact-check/tools/api). Related corpora: the Data Commons ClaimReview downloads – a historical research dataset plus a daily-refreshed feed of markup created via the Fact Check Markup Tool / Read-Write API ([datacommons.org/factcheck/download](https://datacommons.org/factcheck/download)).

**Deprecation status (verified against Google's own pages, 2026-08):** the API itself carries **no deprecation or shutdown notice** – the API docs page is notice-free, and both endpoints remain documented. What *was* deprecated is the **Search feature**: Google's structured-data guide states verbatim "We're phasing out support for `ClaimReview` markup in Google Search. However, this markup remains supported by the Factcheck Explorer Tool" ([source](https://developers.google.com/search/docs/appearance/structured-data/factcheck)). Press coverage dates the rich-result removal to June 2025 ([Nieman Lab](https://www.niemanlab.org/2025/06/google-kills-the-fact-checking-snippet/), [Poynter](https://www.poynter.org/ifcn/2025/google-claimreview-fact-checks-snippets-removed/)). Practical read: the `claims:search` short-circuit and the ADR 0002 escape hatch (`docs/adr/0002-...md`, "the free Google Fact Check Tools API … within ToS") still stand, but the ecosystem *incentive* for publishers to keep emitting ClaimReview markup has weakened – the corpus's freshness is now a risk to monitor, and the API has sat at `v1alpha1` since launch, which is its own maintenance-status signal.

Note the wire format: the API returns `claim.text`, `claim.claimant`, and per-review `publisher`, `url`, `title`, `reviewDate`, `textualRating`, `languageCode` ([reference](https://developers.google.com/fact-check/tools/api/reference/rest/v1alpha1/claims/search)) – i.e. it serves `Rating.alternateName` as `textualRating` and does **not** expose `ratingValue`/`bestRating`/`worstRating`. So the structured half of the rating is available in the underlying ClaimReview markup and the Data Commons feeds, but *not* through `claims:search`. That reframes the issue's "we throw away structured rating scales" point: the throwing-away happens partly at Google's API boundary, not only in our `ratingToStance` (`lib/factcheck.ts:91-99`).

### 1.5 AVeriTeC

**What it encodes:** 4,568 real-world claims (50 fact-check orgs), each with **question–answer pairs** whose answers are backed by web evidence, a **verdict**, and a textual **justification** explaining how the QA pairs combine. Built explicitly to avoid context dependence, evidence insufficiency, and temporal leakage. **Label vocabulary:** exactly four – *Supported*, *Refuted*, *Not Enough Evidence*, *Conflicting Evidence/Cherry-picking* (κ = 0.619). **Aggregate/eval:** the **AVeriTeC score** – verdict accuracy *conditioned* on evidence quality: generated Q+A pairs are matched to gold ones by Hungarian-algorithm-optimal METEOR (hu-METEOR); if the Q+A match is below 0.25 the claim scores 0 regardless of the verdict; at most 10 QA pairs count. Sources: Schlichtkrull et al., NeurIPS 2023 D&B, [arXiv:2305.13117](https://arxiv.org/abs/2305.13117); dataset page [fever.ai/dataset/averitec.html](https://fever.ai/dataset/averitec.html) (CC-BY-NC-4.0); shared-task paper [arXiv:2410.23850](https://arxiv.org/pdf/2410.23850) / [ACL Anthology 2024.fever-1.1](https://aclanthology.org/2024.fever-1.1/) for the metric definition.

This is VERITRACE's closest structural relative: `Source → ClaimItem → QuestionItem → EvidenceItem` is AVeriTeC's claim → QA-pairs → evidence with a document layer on top, and the 4-way `Verdict` union (`lib/graph-types.ts:4`) uses AVeriTeC's exact label set (ADR 0002 chose the golds partly *because* "AVeriTeC already normalised to our exact 4 labels"). One deliberate semantic divergence: ADR 0007 restricts `conflicting` to the **document level** (cherrypicking across claims); a single atomic claim with mixed deciding evidence resolves to NEI (`lib/pipeline/verdict.ts:64-67`). AVeriTeC's *Conflicting Evidence/Cherry-picking* label, by contrast, is a per-claim label in the dataset – ADR 0007 reads mixed-evidence-on-one-proposition as AVeriTeC's NEI, which is a defensible but *interpretive* alignment, not a mechanical one. Eval comparisons on AVeriTeC golds should remember our pipeline can never predict per-claim `conflicting` while the gold set contains it.

### 1.6 FEVER / FEVEROUS

**FEVER:** 185,445 synthetic claims (altered Wikipedia sentences); **labels:** 3-way – *Supported / Refuted / NotEnoughInfo* (Fleiss κ = 0.6841); Supported/Refuted claims carry the gold evidence *sentences*. **Aggregate:** the FEVER score – label correct **and** a complete gold evidence set retrieved (the paper's baseline: 31.87% with evidence required vs 50.91% label-only). Source: Thorne et al., NAACL 2018, [arXiv:1803.05355](https://arxiv.org/abs/1803.05355). **FEVEROUS:** 87,026 claims extending evidence to **structured data** – table cells as well as sentences – same 3-way labels; the FEVEROUS score again requires correct evidence + verdict (baseline 18%). Source: Aly et al., [arXiv:2106.05707](https://arxiv.org/abs/2106.05707).

FEVER matters to VERITRACE mostly as ancestry: our `Verdict` minus `conflicting` *is* the FEVER label set, our `nei` takes FEVER's name, and the "evidence must be retrieved, not just the label right" scoring philosophy is what `GoldenGold.keyEvidenceUrls` (`evals/golden/schema.ts:59`) exists to support. FEVER's synthetic Wikipedia-only claims make it a poor gold source for us (ADR 0002 picked AVeriTeC for exactly the reasons FEVER falls short: artificial claims, temporal leakage).

### 1.7 ClaimBuster

**What it encodes:** *check-worthiness* of individual sentences – a screening step before any verification. **Vocabulary:** 3 classes – NFS (non-factual), UFS (unimportant factual), CFS (check-worthy factual); the deployed system emits a continuous **check-worthiness score in [0, 1]** (the classifier's CFS probability) used to rank sentences. Trained on 20k+ human-labeled US-debate sentences. Source: Hassan et al., *Toward Automated Fact-Checking: Detecting Check-worthy Factual Claims by ClaimBuster*, KDD 2017, [PDF](https://ranger.uta.edu/~cli/pubs/2017/claimbuster-kdd17-hassan.pdf) / [ACM DL](https://dl.acm.org/doi/pdf/10.1145/3097983.3098131).

VERITRACE re-derives this pipeline stage with three separate fields on `ClaimItem`: `checkworthy` (subjective/opinion/prediction → not check-worthy, `lib/graph-types.ts:80-81` – ClaimBuster's NFS), `relevant` (trivial presupposition → factual but not load-bearing, `:82-89` – close cousin of UFS), and the continuous `relevanceScore` (0..1 triage ranking driving `capSearchable`, `:90-96` – the direct analogue of ClaimBuster's score). Our decomposition is finer than ClaimBuster's (we also carry `checkable` for provenance-type claims the text-only build can't check, `:79`), but the score semantics differ subtly: ClaimBuster's number is a *check-worthiness probability*; our `relevanceScore` is a *load-bearingness/contestedness* ranking used for capping. They correlate but are not the same quantity – worth remembering if we ever report "check-worthiness" numbers against ClaimBuster baselines.

### 1.8 ClaimsKG

**What it encodes:** an RDF knowledge graph (~28k claims, 6.6M triples at publication) harvested from fact-checkers' ClaimReview markup, entity-linked to DBpedia, with claim coreference resolution and – the load-bearing part for us – **normalized truth ratings** across heterogeneous publisher scales (TRUE / FALSE / MIXTURE / OTHER), while keeping the original rating. Sources: Tchechmedjiev et al., ISWC 2019, [PDF](http://users.ics.forth.gr/~fafalios/files/pubs/ISWC2019_ClaimsKG.pdf); live graph at [data.gesis.org/claimskg](https://data.gesis.org/claimskg/). ClaimsKG is precedent for exactly the design our golds already use – keep `originalRating` verbatim, map to a coarse normalized enum, keep the mapping auditable (`evals/golden/schema.ts:39-41`) – and a cautionary tale for `ratingToStance`, which does the same normalization with a substring list and *without* retaining anything but the raw string (`lib/factcheck.ts:58-99`).

### 1.9 MediaReview

**What it encodes:** a schema.org `Review` subtype for fact-checking **media items** (images/video/audio) rather than textual claims – `mediaAuthenticityCategory` drawing from `MediaManipulationRatingEnumeration` (*OriginalMediaContent, DecontextualizedContent, EditedOrSyntheticContent, ImitationContent, SatireOrParodyContent, StagedContent, TransformedContent*) plus `originalMediaLink`; linked from ClaimReview via `associatedMediaReview`. Still flagged as a new/in-progress definition on schema.org. Source: [schema.org/MediaReview](https://schema.org/MediaReview). VERITRACE has no media pipeline by design – this is precisely the `checkable: false` / `provenance` territory the golds stratify out (`evals/golden/schema.ts:82-84`). MediaReview matters to us only as the *name* for that excluded category: if we ever emit ClaimReview, marking provenance-type claims as out-of-scope-because-MediaReview-territory is the standards-aligned way to say it.

### 1.10 IFCN

**What it standardizes:** *process*, not labels. The IFCN Code of Principles ([ifcncodeofprinciples.poynter.org](https://ifcncodeofprinciples.poynter.org/)) binds signatories to transparency of sources, funding, and **methodology** (same standard and process for every check, evidence dictates conclusions), assessed against 31 criteria – but imposes **no shared rating vocabulary**; signatories keep their own heterogeneous scales ("half true", "three Pinocchios", "Distorcido"). There is no IFCN label taxonomy to map onto. The relevant alignment for VERITRACE is methodological: our stated-not-learned verdict rules (`lib/pipeline/verdict.ts:4-15`), the visible `QuestionTrace`, and the advisory rationale are the machine analogue of IFCN's methodology-transparency commitments, and IFCN signatory status is a reasonable future criterion for the curated `FACT_CHECKERS` trust list used at `lib/factcheck.ts:101-103`.

## 2. Mapping VERITRACE onto each standard

### 2.1 Vocabulary crosswalk (per-claim labels)

| VERITRACE `Verdict`  | AVeriTeC                          | FEVER/FEVEROUS  | FActScore       | SAFE            | ClaimsKG normalized | ClaimReview                                  |
| -------------------- | --------------------------------- | --------------- | --------------- | --------------- | ------------------- | -------------------------------------------- |
| `supported`          | Supported                         | Supported       | supported       | supported       | TRUE                | free text (`alternateName`) + numeric scale  |
| `refuted`            | Refuted                           | Refuted         | not-supported   | not-supported   | FALSE               | free text + numeric scale                    |
| `conflicting`        | Conflicting Evidence/Cherry-pick. | –               | –               | –               | MIXTURE (roughly)   | "Mixture"/"Half true" style labels           |
| `nei`                | Not Enough Evidence               | NotEnoughInfo   | –               | –               | OTHER (roughly)     | "Unproven"/"Unverified" style labels         |
| (dropped: `relevant: false`) | –                         | –               | –               | irrelevant      | –                   | –                                            |

Divergence flags: (a) post-ADR-0007, `conflicting` is document-level only – VERITRACE can never emit it per-claim, while AVeriTeC golds contain it per-claim; (b) FActScore/SAFE's binary/3-way collapses our `nei` and `refuted` into "not-supported" – a FActScore-comparable number from a `ClaimTally` must be `supported / total`, treating NEI as failure, which is harsher than our UI's framing of NEI as abstention; (c) SAFE's "irrelevant" maps to our `dropped` count, which we correctly keep out of `total` (`lib/graph-types.ts:109-110`) exactly as SAFE keeps irrelevant facts out of F1@K.

### 2.2 Structural mapping (per standard)

| Standard        | Their unit                              | Our unit                                      | Alignment                                                                                                                                                             |
| --------------- | --------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FActScore/SAFE  | generation → atomic facts → binary      | `SourceTextItem → ClaimItem[]` → 4-way        | Same decompose-then-check shape; `ClaimTally` ≈ the FActScore numerator/denominator; `audit.ts` flags instead of auto-correcting (deliberate, documented)              |
| ClaimReview     | one review of one claim                 | one resolved `ClaimItem` + evidence + rationale | Near-lossless to emit (see §2.3); lossy to consume via `claims:search` (no numeric rating on the wire; we then substring-match the text)                              |
| Google FCT API  | `claims:search` hit list                | `FactCheckHit` (`lib/factcheck.ts:26-42`)     | Faithful to the wire format; the flattening to `Stance` happens in `ratingToStance` and discards "Mostly true" vs "True" granularity                                  |
| AVeriTeC        | claim → QA pairs → verdict + justification | `ClaimItem → QuestionItem[] → EvidenceItem[]` + `rationale` | Structurally isomorphic (their answer text ≈ our `EvidenceItem.passage`; their justification ≈ our `rationale`); label semantics diverge on per-claim `conflicting` |
| FEVER/FEVEROUS  | claim + label + gold evidence set       | claim + verdict + `keyEvidenceUrls` (golds)   | Our eval philosophy (verdict must be evidence-backed) is FEVER-score-shaped; live pipeline has no closed evidence universe so a strict FEVER score is undefined for us |
| ClaimBuster     | sentence → CFS score [0,1]              | `checkworthy` + `relevant` + `relevanceScore` | We split their one scalar into three orthogonal booleans/scores; finer but not directly comparable                                                                     |
| ClaimsKG        | ClaimReview corpus → normalized enum + original | golds: `originalRating` + 4-way `Verdict`  | Same keep-the-original-rating discipline in the golds; **absent** in the live `FactCheckHit`, which keeps `textualRating` but no normalized-rating audit trail beyond `Stance` |
| MediaReview     | media item + manipulation enum          | `checkable: false` claims                     | We name the exclusion; they name the categories. No overlap in what we can check                                                                                        |
| IFCN            | process commitments                     | stated verdict rules + traces                 | Philosophical alignment; also a candidate criterion for `FACT_CHECKERS` curation                                                                                        |

### 2.3 What speaking each natively would buy

**Emitting ClaimReview (JSON-LD per resolved claim)** – the highest-value export. A resolved `ClaimItem` maps nearly losslessly: `claimReviewed` ← `ClaimItem.text`; `itemReviewed` (a `Claim`) with `appearance` ← the source text and `datePublished` ← `ClaimItem.date`; `reviewRating.alternateName` ← our verdict label with `ratingValue` on a declared 4-point scale; `reviewBody` ← `rationale`; `citation`/`isBasedOn` ← the evidence URLs. Two honesty caveats: our verdict is *advisory and machine-generated*, and ClaimReview's ecosystem assumption is a human editorial process (IFCN-style) – an export should say so in `reviewBody` or an `author` `@type` that doesn't impersonate a human fact-checker; and `conflicting` only exists at source level, so a source-level ClaimReview (the whole paste as `itemReviewed`) is the natural place for it, with per-claim reviews carrying only supported/refuted/nei. What it buys: every downstream ClaimReview consumer (Data Commons, ClaimsKG-style harvesters, research tooling) can read a VERITRACE run; it is the honest interchange form of "advisory verdict + evidence trail". The June-2025 Search deprecation removes the SEO incentive but not the interchange value.

**Consuming ClaimReview structurally** – within `claims:search` the ceiling is low (no `ratingValue` on the wire), so the realistic upgrades are (a) replace the `ratingToStance` substring lists with a maintained normalization table that also records the *normalized rating* (ClaimsKG-style TRUE/FALSE/MIXTURE/OTHER) on `FactCheckHit`, keeping the mapping auditable the way `GoldenSource.originalRating` already does; (b) for bulk/gold use, prefer the Data Commons feed, which carries full markup including numeric ratings – that is also the ADR 0002 escape hatch for post-2023 golds.

**FActScore-comparable reporting** – define and emit `supportRatio = supported / total` from `ClaimTally` alongside the categorical `sourceVerdict`, with the stated caveat that NEI counts against the ratio in FActScore's frame. Cheap (one derived number) and makes eval output citable against published FActScore baselines.

**AVeriTeC-score-style eval** – our golds already carry `questions[].keyEvidenceUrls`; grading verdict accuracy *conditioned* on question/evidence match (their hu-METEOR@0.25 gate) is implementable against `GoldenQuestion` and would align our eval headline number with the shared-task literature instead of bare verdict accuracy.

## 3. Open questions and recommended follow-ups

1. **Structured `FactCheckHit` normalization** (`lib/factcheck.ts`): add a `normalizedRating` field (TRUE/FALSE/MIXTURE/OTHER, ClaimsKG-style) recorded alongside `textualRating`, and move `ratingToStance` onto that normalization table – the current substring lists are the String-Parsing Smell the user-level instructions name, and every new publisher scale arrives as a new substring today.
2. **ClaimReview JSON-LD export**: one export function per resolved claim + one per source, with explicit machine-authorship marking. Decide the `Rating` scale declaration (`worstRating: 1, bestRating: 4`? ordinal order of nei/conflicting is ill-defined – possibly `alternateName`-only, which Google's guide permits since only `alternateName` is required).
3. **`supportRatio` in eval + UI reporting**: derive from `ClaimTally`; document the NEI-counts-against caveat.
4. **AVeriTeC-score harness**: implement the conditioned-accuracy metric over `GoldenQuestion.keyEvidenceUrls`; also decide the scoring rule for AVeriTeC golds labeled per-claim *Conflicting* given the pipeline can never predict it (options: remap those golds to NEI per ADR 0007's reading, or stratify them out like provenance items).
5. **Monitor the ClaimReview corpus post-June-2025**: with Search rich results gone ([Google's notice](https://developers.google.com/search/docs/appearance/structured-data/factcheck), [Poynter](https://www.poynter.org/ifcn/2025/google-claimreview-fact-checks-snippets-removed/)), publisher markup volume may decay; the short-circuit's hit rate and the ADR 0002 escape hatch both depend on it. Track hit-rate in runs; keep the Data Commons feed URL as the fallback corpus.
6. **`relevanceScore` semantics**: decide whether it means check-worthiness (ClaimBuster's probability) or load-bearingness (its current doc comment) – today it drives capping only, but the moment we report it against external baselines the ambiguity becomes a comparability bug.
